# Дослідження → рішення власника → знання

## Сценарій

1. `research_analyst` завершує крок. Збереження research-артефакта через `worker_complete` атомарно створює кандидатів. Статус кандидата — `candidate`, до знань агентів він не потрапляє.
2. На сторінці «Знання» PAVUTYNA видно твердження, джерела, цитати, рівень доступу й посилання на оригінальне дослідження.
3. Власник задає дату актуальності та схвалює факт або відхиляє його з поясненням. Editor/viewer не можуть прийняти рішення ні через форму, ні через SQL-функцію.
4. Схвалення створює один затверджений документ Hub та один запис `approvals` зі scope `knowledge_candidate`, зберігає автора рішення й подію аудиту. Повторний однаковий клік не дублює записи; протилежне рішення після розгляду відхиляється.
   Форма передає відбиток переглянутого запису: якщо твердження або джерела змінилися після відкриття сторінки, потрібно оновити її перед рішенням.
5. Строк включає зазначений день за Europe/Kyiv. Наступного дня запис зникає з `worker_context.knowledge` та `governance.knowledge_refs`. Документ залишається видимим власнику з позначкою про завершення строку.

## Джерела й права

- Підтримуються `KnowledgeCandidate.v1.candidates` та чинний `research_candidates[]` (`proposed_fact`, `url`, `retrieved_at`, `excerpt`). Походження — незмінні research artifact, step, run, workspace та індекс у вихідному масиві.
- Імпорт нових артефактів увімкнено лише для workspace зі slug `pavutyna` та ролі `research_analyst`. Це навмисне обмеження `stage_research_artifact` для поточного пілота: поширення на інші workspace потребує окремого рішення й тестів ізоляції. Звичайні артефакти й інші робочі простори не створюють кандидатів.
- Старий research із придатним HTTP(S)-джерелом отримує `reported`; із непридатним джерелом — `assumption`, його схвалити не можна. Сирий оригінал залишається в research-артефакті. Статус `verified` автоматично не надається.
- Клас кандидата не може автоматично стати нижчим за клас вихідного запиту. Персональні знання не публікуються. RLS ізолює робочі простори; термінальні статуси пише лише `office.review_knowledge_candidate` після перевірки власника.
- Після розгляду кандидат незмінний. Для виправленого твердження потрібна нова версія дослідження; зміна існуючих схвалених документів Hub зберігає чинну модель прав P0.
- Некоректний канонічний кандидат відхиляє всю транзакцію завершення кроку: частково імпортованих результатів не залишається. Ручного backfill старих артефактів цей етап не виконує.

## Уже підготовлені задачі та CMO

Gateway не віддає повний контекст задачі з простроченим посиланням і не дозволяє її взяти: GET/CLAIM повертають окрему причину `knowledge_expired`; обмеження провайдера зберігає `data_class_above_provider_policy`.

Кожен worker tick через `worker_claim → worker_reap` повертає таку задачу з `awaiting_agent` (або `ready` зі старою відповіддю) у `ready`, очищує старі prompt/response та відкликає старі оренди. Наступний прохід збирає prompt без простроченого знання й знову паркує задачу для виконавця. У стрічці власника з'являється `step.knowledge_expired` зі зрозумілим поясненням. Для відновлення не потрібен ручний перезапуск. Паралельно заблоковані кроки/оренди пропускаються без очікування й обробляються наступним tick; повторні проходи не дублюють подію.

Відповідь за відкликаною орендою зберігається лише як пропозиція з причиною `knowledge_expired`; вона не змінює перепідготовлений крок або нову оренду. Дані, вже прочитані виконавцем, та історичні артефакти фізично не переписуються.

CMO отримує живий контекст із чинних дозволених записів Hub, обмежений тими самими ID і версіями, що були дозволені для підготовленої задачі. Нові або змінені записи вимагають нової підготовки задачі. Статичний файл із P1 залишається рецензованим прикладом у skill pack; MCP не використовує його як джерело поточних фактів. `context.version` — SHA-256 фактично переданого тексту.

Виконавцю передаються лише п'ять файлів: `SKILL.md`, `checklist.md`, `rubric.json`, `examples/good.md`, `examples/bad.md`. Еталони `evaluation/golden-briefs.json` зберігаються для оцінювання й не входять до `skills[].files` або його SHA-256. Клас контексту дорівнює `envelope.data_class`. Якщо файл навички недоступний, GET/CLAIM повертає початковий envelope без вкладень; `console.warn` містить лише ID задачі та код помилки, а вже видана оренда зберігається.

## Доставка й перевірки

0009 залишається у `supabase/drafts/0009_office_research_concepts.sql`, поза автоматичними міграціями. Вона містить нові таблиці/права/тригери та розширює тіла `worker_context`, `worker_reap`, `gateway_policy_ok`, `gateway_get`, `gateway_claim`, `gateway_submit`, зберігаючи їхні сигнатури й P0-політики. Наявні колонки та функції не видаляються й не перейменовуються.

До застосування 0009 сторінка працює на 0008: колонки строку читаються через JSON-представлення рядка, а секція досліджень з'являється лише за наявності функції перевірки. П'ять MCP-інструментів та їхні схеми входу збережені. UI/API для scope `concept`/`run` поза цим етапом.

Власник обрав ізольовану локальну PostgreSQL 16 замість окремої хмарної staging-бази. `npm run test:sql` створює окрему БД і прибирає її після тестів; два набори `50_*` перевіряють права, атомарний імпорт, рішення, аудит та прострочення.

Для MCP E2E запускаються обидві конфігурації з локальним `E2E_ADMIN_URL`: звичайна 0008 та `E2E_DRAFT_0009=1`. Застосування чернетки в E2E виконується лише в тимчасовій БД сценарію. Unit-тести перевіряють форму власника, приховані дії інших ролей, екранування джерел та сумісність із відсутньою 0009.

Перед продакшеном потрібні рев'ю PR, окреме погодження застосування 0009, резервна копія та перевірка живих виконавців після міграції. Відкат коду не потребує видалення нових таблиць: імпорт/рішення можна зупинити відкликанням доступу до нової функції та вимкненням нового тригера. Автоматичного rollback або застосування чернетки цей PR не запускає.
