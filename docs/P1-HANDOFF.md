# P1: контракти, stubgen, CMO, чернетка 0009

## Поточна поведінка

- До бібліотеки додано 16 `$defs`: 9 контрактів і 7 допоміжних визначень. `KnowledgeRef` використовується чинний.
- Усі дев'ять контрактів зареєстровано для перевірки результатів MCP під звичайними іменами та версіями `.v1`. Невалідна відповідь відхиляється до запису результату; оренда зберігається для виправлення. Це перевірено через реальний MCP handler на локальній БД.
- `validate.mjs .` перевіряє приклади та дозволяє збіг імен лише для ідентичних визначень. Будь-яка різниця з рецензованим джерелом є конфліктом.
- Stubgen підтримує типові ідентифікатори, UUID, дати, символьні класи, групи, квантифікатори, `format: uuid/date/date-time/uri`. Складні непідтримувані регулярні вирази завершуються явною помилкою. Це детермінований генератор тестових даних, а не загальний розв'язувач JSON Schema.
- `skills/cmo/` — копія рецензованого пакета 1.0.0. Для `seat=strategist`, `step=diagnosis`, workspace `pavutyna`, класу `internal/confidential` сервер додає `skills[]` і `context` у відповіді GET/CLAIM. Пакет містить приклади PAVUTYNA, тому в інші робочі простори не передається.
- Завантажувач отримує workspace з чинного `worker_context` лише після успішної авторизації GET/CLAIM. Набір п'яти інструментів і їхні схеми входу збережені. Кроки плейбуків v1 не отримують нових полів.
- `sha256` — хеш JSON-масиву відсортованих `[шлях, текст]` для шести переданих файлів. CRLF нормалізуються до LF. `context.version` — SHA-256 тексту контексту, а не версія живого Knowledge Hub. Контекст є рецензованим статичним зрізом від 19.10.2026; автоматичного оновлення тут немає.

## Чернетка 0009

Файл `supabase/drafts/0009_office_research_concepts.sql` навмисно розміщений поза `supabase/migrations/`. Звичайне застосування міграцій його не підхоплює. Застосовувався лише до тимчасової локальної тестової бази.

- `knowledge_candidates` — окремий staging для результатів `research_analyst`, зі статусом `candidate`. Рецензований JSON-контракт залишається незмінним; його коментар про збереження у `knowledge_docs.status=draft` описує старий проєктний варіант. Адаптер імпорту з research-артефактів у staging — наступний етап.
- Лише власник може перевести кандидата в `approved/rejected`. При схваленні тригер атомарно створює затверджений запис Hub, зберігає посилання, автора рішення, строк дії й клас даних. Припущення без підтвердження, прострочені дані й персональні дані не публікуються. Після рішення кандидат незмінний.
- Нові типи знань зберігаються в кандидатові; для сумісності Hub отримує `fact` для фактів і `other` для решти типів. Джерела й походження залишаються у staging.
- `knowledge_docs.valid_until` додається без зміни чинних функцій. Автоматичне виключення знань після завершення строку з `worker_context` потребує окремого наступного кроку перед увімкненням цього процесу в проді.
- `concepts` має збережений `concept_status`; `production_status/release_status` не додаються. Рішення щодо вибору концепції належить власнику. Тригери перевіряють workspace/run/artifact.
- `approvals.scope/target_id` опційні для сумісності. Нові scope: `run`, `concept`, `knowledge_candidate`. Чинний `office.decide` збережений; UI/API для нових scope ще не підключено.
- На нових таблицях увімкнено RLS; видалення користувачам не надане. Нові тригерні функції мають права викликача й закриті для прямого виклику.

## Локальні перевірки

`npm run test:sql` працює через TypeScript/Postgres.js без залежності від bash/psql. Приймає `E2E_ADMIN_URL` лише з локальним хостом, створює окрему тимчасову БД, виконує 0001–0008, старі SQL-тести, потім чернетку 0009 і `50_*`; після завершення видаляє лише цю БД. `tests/sql/run.sh` залишено як сумісну точку входу.

Для E2E використовується локальний PostgreSQL 16, фіктивні акаунти й stub/session providers. Зовнішні генеративні API не викликаються.
