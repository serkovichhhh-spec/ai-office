# AI Office: аудит ролей і виправлення процесів

Це первинний аудит і звіт етапу профілів. Поточна реалізація, актуальні перевірки й порядок rollout описані в [CLAUDE_TAKEOVER_REPORT.md](CLAUDE_TAKEOVER_REPORT.md). Наведені нижче числа тестів і висновки про міграції стосуються лише початкового етапу.

Дата: 19.10.2026. База перевірки: commit `59be3ae`, із включенням паралельного виправлення `26eb294`; код усіх 12 плейбуків, чинні agents і knowledge_docs workspace PAVUTYNA, пакет рев'ю білборду. Робоча архітектура: Seat + Execution Gateway + Versioned Blackboard. Платні API не додаються.

## Ієрархія і відповідальність

Власник визначає мету, ухвалює бізнес-рішення й остаточно затверджує результат. CMO відповідає за весь запуск. Арт-директор керує творчою реалізацією, коли вона потрібна в обраному графі. QA звітує незалежно власнику. Усі ролі не запускаються на кожну задачу; склад визначений плейбуком.

| Роль | Керівник | Обов'язковий результат |
|---|---|---|
| CMO / orchestrator | Власник | Продуктовий бриф, декомпозиція, залежності, критерії та рекомендація |
| Стратег | CMO | Сегмент, інсайт, пропозиція, докази, повідомлення, CTA |
| Дослідник | CMO | Метод, порівнювані факти, джерела і дати, висновки та прогалини |

| Арт-директор | CMO | Творчі території, візуальна логіка, завдання реалізаторам |
| Креативник | Арт-директор | Різні ідеї з механікою, роллю бренду і відбором |
| Копірайтер | Арт-директор | Повні тексти для потрібного каналу, аргументація, CTA й умови |
| Сценарист | Арт-директор | Драматургія, кадри, текст, звук, таймкоди й здійсненність |

| Ads-спеціаліст | CMO | Структура кампанії, аудиторії, бюджетний план, оголошення і вимірювання |

## Внесені зміни

1. Версійні професійні контракти для всіх 16 ролей. Роль поточного кроку завжди передається, workspace prompt її більше не стирає.
2. Нові версії 12 плейбуків: `intake -> marketing_brief (CMO, ChatGPT) -> prepare -> build -> review -> package`. Старі номери і графи збережені для чинних запусків. У каталозі пропонуються лише нові версії.
3. MarketingBrief містить 9 тематичних блоків: компанія, продукт, переваги, умови, покриття, бренд, аудиторія, конкуренція, вимірювання. Для кожного: стан, зміст, джерела й обмеження. Окремо: стратегічний вибір, реальний шлях клієнта, завдання і критерії для кожного етапу, попередні рішення, прогалини з відповідальними.
4. Сервер перевіряє кількість і унікальність блоків, відповідність виконавців графу, критичні джерела для типу задачі, відсутність суперечності ready/blocking, ID/version/JSON Pointers. Явна заглушка «ЦА» не є достатнім сегментом.
5. Без достатнього чинного брифу виконавець не запускається. Якщо джерела змінилися, пакет блокується. Невідомі обов'язкові артефакти більше не пропускаються мовчки у нових графах.
6. Бриф CMO отримують prepare, build і review. Правки власника зберігаються артефактом і проходять ланцюг; revision_intake починає з CMO.
7. Рев'ю нових графів повертає дефект до CMO, prepare або build за адресою проблеми. Ліміт циклів залишається обмеженим. Ремонт раннього етапу повторно виконує залежні етапи.
8. Авторські кроки нових графів виконує ChatGPT, незалежне рев'ю - Claude Session. Змін default_executor чинних ролей не потрібно; старі маршрути залишаються як були. Автоматичні API-витрати не додаються.
9. Старе рев'ю рілсів тепер отримує стратегію й попередній review. Старі пакети з revise / stub не позначаються готовими до затвердження.
10. Новий пакет перевіряє рішення рев'юера, поточні ID/version матеріалу і стан брифу. Передані джерела та реально процитовані джерела показані окремо. Текстовий структурований результат не вважається візуально перевіреним файлом.
11. Відсутня або вимкнена AI-роль викликає явну помилку конфігурації. Детерміновані кодові кроки не видаються за AI-роботу.
12. В офісі доступні обов'язки, компетенції, результат і керівник кожної ролі. Виробничі ролі, які вже працюють у плейбуках через сесії, не показуються безумовно як очікування локального моста. Прибрано загальний підпис, який називав будь-яку нову задачу рілсами.

## Чинна конфігурація PAVUTYNA

Профілі застосовані адресно у workspace PAVUTYNA через DML без зміни схеми: 16 ролей, 16 повних інструкцій із методами, provenance `role-contracts:2026-10-19.2`. Додані дослідник і performance-аналітик. Попередні 14 профілів збережено перед зміною; записи конфігурації в office.events: 113 (профілі), 114 (повні методи). Існуючі default_executor, enabled і користувацькі назви не змінені.

Повторюваний механізм для нових workspace:

```bash
node --import tsx scripts/role-contracts-sql.ts <workspace-slug> > role-contracts.sql
```

Скрипт сам не підключається до БД. Оператор читає й застосовує DML. Користувацькі профілі з іншою provenance зберігаються; зміни журналюються. Для наявних офісів це окремий DML-крок. Нова bootstrap-міграція з Implementation Plan v1 уже створює 16 повних профілів для нових офісів. Приватні локальні скіли Claude не змінюються.

## Перевірка і практичні межі

- Базові тести до змін: 35/35.
- Після змін та суміщення з `26eb294`: 58/58 unit/contract tests, TypeScript і production build проходять.
- Усі 12 нових графів перевірені session-like fixtures із повним брифом і валідними посиланнями. Перевірені відсутній/застарілий контекст, заглушки, адресне повернення, збереження правок, незалежний виконавець, невалідний пакет і вимкнені ролі.
- Readback робочої БД підтвердив 16/16 версійних профілів.
- Fixture не доводить рівень реальних ідей, текстів, досліджень або дизайну. Профіль не є завантаженою професійною базою знань і не створює інструментів.
- Поточний backend не має універсального пошуку всіх файлів/чатів користувача. CMO бачить approved knowledge workspace, артефакти й інструменти своєї сесії. Інші матеріали потребують реального імпорту/адаптера; їх відсутність у пакеті позначається context_not_delivered, а не відсутністю фактів у компанії.
- Повний бриф за потреби містить дослідження, але контракт не може автоматично довести правдивість кожного висновку. Нові зовнішні джерела не стають approved knowledge автоматично.
- Дизайн/відео контракти переважно видають специфікації. Створення файлів та візуальна перевірка потребують відповідного інструмента й реального виробничого кроку. `file_quality_verified=false` це фіксує.

## Наступна перевірка на реальній роботі

Після розгортання вибрати по одному реальному кейсу: білборд, IVR/текст, рілс, аналіз кампанії, запуск оффера. Для кожного перевірити достатність CMO-брифу, отримання контексту спеціалістом, джерела й умови, відповідність носію, адресність правок та перевірку кінцевого результату. Окремо перевірити готові файли там, де вони потрібні.

Для поточного білборду потрібен новий запуск outdoor_print_pack актуальної версії з посиланням на попередній запуск і рішення власника. Не змінювати playbook_version заднім числом і не видавати старий reels-пакет за виправлений OOH.

Невдалий приклад фіксувати як окремий дефект конкретного контракту/навику/інструмента. До проходження цих реальних кейсів не оголошувати весь офіс професійно атестованим.

## Розгортання і відкат

Нові графи не вимагають міграції БД: чинні playbook_version, artifact.kind, agents і worker вже підтримують ці значення. Потрібне розгортання коду. Поточні запуски не перезапускаються та зберігають номери версій. При відкаті коду спочатку зупинити створення нових запусків, завершити або явно призупинити запуски нових версій: старий commit не знає цих номерів. Не видаляти версійні артефакти. Для профілів відновити попередню конфігурацію з передзмінного snapshot лише за відсутності подальших змін.
