# AI Office PAVUTYNA: бібліотека плейбуків

Версія специфікації: 2026.10.19-v1. Статус: пропозиція для реалізації Claude, не встановлена зміна рушія. Вихідні обмеження - поточний запит власника. Конкретний брендбук і його факти тут не відтворюються: вони завантажуються з актуального затвердженого knowledge під час запуску.

## Комплект

- `playbooks.yaml`: 12 документів YAML з усіма полями заданого шаблону.
- `schemas.json`: 58 спільних визначень JSON Schema Draft 2020-12, включно з усіма результатами кроків.
- `brief-schemas.json`: повні схеми брифу для кожного плейбука.
- `registry.json`: версії, пріоритети, головний масив результату й ліміти deliverable_count.
- `semantic-rules.md`: обов'язкові перевірки понад JSON Schema.
- `validate_spec.py`: перевірка цілісності пакета стандартною бібліотекою Python.

`$ref: schemas.json#/$defs/Preparation` - точне посилання на схему, а не довільна назва типу. Всі властивості описаних об'єктів обов'язкові, `additionalProperties=false`. Де даних може не бути, передбачено явний `null` або порожній масив. Не розіменовувати URL схеми через мережу: зареєструвати локальний файл у валідаторі або вбудувати його `$defs` у схему кроку. YAML сам не є TypeScript-реєстром: Claude імпортує/компілює ці фіксовані визначення в код та використовує звичайний серверний валідатор рушія.

## Ролі й виконавці

Додати лише `scriptwriter` - сценарії, таймкоди й драматургія; `ads_specialist` - структура реклами, оголошення й експерименти. `media_buyer` поки не потрібен: закупівля та управління реальним бюджетом залишаються людським виконанням. Копірайтер покриває PR, SMS, email, IVR та сайт без додавання зайвих seats.

Seat не є executor. `designer` можна лишити загальним UI-аліасом, але ці кроки призначаються конкретно `graphic_designer` або `print_designer`. `ads_manager`, `print`, `smm` у handoff - адресати передачі, а не нові значення executor.

У нових визначеннях два авторські кроки мають одного executor, рев'ю - іншого. Для стратегії/аналітики автор ChatGPT, reviewer Claude; для креативу/сценаріїв автор Claude, reviewer ChatGPT. Це виключає саморев'ю вхідної стратегії тією ж моделлю. Існуючий пілот reels_concepts v1 з маршрутом ChatGPT -> Claude -> ChatGPT зберігається незмінним для старих запусків. Нова специфікація цього ключа має version=2 і застосовується лише до нових запусків після впровадження. Ключі решти плейбуків мають version=1.

## Фіксований граф, спільний для всіх плейбуків

`steps` містить авторські AI-вузли, `review` - декларацію неявних вузлів рев'ю. Кожен вузол повертає рівно один JSON-об'єкт. Пакування, перевірки й передача є code-вузлами; погодження - human-вузлом. Жоден AI не додає вузли під час виконання.

Компілювати наперед такі вузли:

1. `input_gate` (code): валідація брифу, доступів, версій і обов'язкового knowledge.
2. `prepare` (AI за YAML): план/вихідні напрями.
3. `build` (AI за YAML): повний пакет матеріалів.
4. `review_1` (reviewer за YAML): ReviewDecision.
5. `revise` (той самий seat/executor і output_schema, що build): єдине доопрацювання.
6. `review_2` (той самий незалежний reviewer): ReviewDecision.
7. `package` (code): збірка останніх валідних версій без переписування контенту.
8. `owner_decision` (human): approve / request_changes / reject / resolve_inputs.
9. `handoff` (code): створення пакета для визначеного адресата.

Умовні ребра фіксовані:

| Звідки | Умова | Куди |
|---|---|---|
| input_gate | Усі обов'язкові входи валідні | prepare |
| input_gate | Бракує knowledge або є конфлікт | package, тип blocked |
| prepare | status=ready | build |
| prepare або build або revise | status=blocked | package, тип blocked |
| build | Серверні й семантичні перевірки пройдені | review_1 |
| review_1 | pass | package, тип ready_for_approval |
| review_1 | revise | revise |
| review_1 | escalate | package, тип escalated |
| revise | Перевірки пройдені | review_2 |
| review_2 | pass | package, тип ready_for_approval |
| review_2 | revise або escalate | package, тип escalated |
| package | Будь-який тип | owner_decision |
| owner_decision | approve + ready_for_approval + gates дійсні | handoff |
| owner_decision | reject | Завершити rejected |
| owner_decision | request_changes або resolve_inputs | Закрити поточний run; новий versioned run із посиланням на попередній |

`package -> owner_decision` відбувається і для блокування: власник бачить конкретні питання й чернетку, але кнопка production approval для неї недоступна. Відповідь власника не запускає безмежний AI-цикл. Новий run потребує явної дії, а не автоматичного повтору.

Структурно невалідний JSON не зберігається як артефакт. Автор отримує повідомлення валідації в тій самій спробі й виправляє формат; це не є новим колом змістового доопрацювання. До виправлення залежні кроки не відкриваються. Status=ready з невиконаними семантичними gates так само відхиляється; критична нестача входів повертається як blocked.

`revise` має inputs: brief, knowledge, artifact:prepare, artifact:build, artifact:review_1. Task: виправити всі critical/major і погоджені minor за issue IDs; повернути повний замінний результат, не patch. Напрям підготовки може бути скоригований у фінальному build лише в межах того самого брифу; матеріальна зміна мети/пропозиції/knowledge вимагає нового run. `review_2` отримує новий артефакт, review_1 та попередній build. Перевіряє усунення issues і регресії. Нові зауваження допустимі лише для критичних порушень, пропущених раніше, або внесених доопрацюванням.

Звичайний прохід має 3 AI-кроки, прохід із доопрацюванням - 5. Для виправлення фактів або входів не вигадувати дані й не перезапускати prepare автоматично: blocked/escalated до власника.

## Evidence-based review

Вихід рев'ю завжди `$defs/ReviewDecision`. Шкала 1-5: 1 - непридатно; 2 - суттєві проблеми; 3 - потрібне змістове доопрацювання; 4 - критерій виконано, можливі некритичні зауваження; 5 - критерій повністю виконано з доказами. Всі п'ять criteria з YAML оцінюються окремо, середній бал не використовується.

`pass`: evidence=5; інші scores>=4; немає open critical/major; немає блокуючих source/brand/format/permission питань. Minor дозволені лише коли прямо пояснено, чому вони не блокують виконання. Critical: неправдиве твердження, невірна ціна/покриття/CTA, відсутність обов'язкового джерела/прав, порушення даних. Major: невиконаний обсяг, непридатна композиція або сценарій, некоректна метрика чи неможливий продакшн. Minor: необов'язкове стилістичне покращення.

Якщо без зміни knowledge/брифу виправити неможливо - escalate. Інакше review_1 повертає revise. Після єдиного доопрацювання невиконані критерії завжди ведуть до escalated. Сервер обчислює маршрут із scores/issues/gates, а не довіряє одному слову decision. Суперечливий ReviewDecision відхиляється на валідації.

Кожне issue: artifact_pointer (JSON Pointer), точний fragment, criterion, severity, конкретний fix. Для пропущеного поля fragment може бути '<missing>', pointer вказує на очікуване поле. Для другого рев'ю resolved_issue_ids мають існувати у review_1; нерозв'язані issues повторюються з тим самим ID. Для першого рев'ю resolved_issue_ids=[]. Незалежний reviewer отримує бриф і фактичні артефакти, але не самооцінку автора. Числові бали creative_ideation є предметом перевірки; reviewer спочатку фіксує незалежну оцінку і лише потім зіставляє її з авторською.

## Knowledge та джерела

Кожен run фіксує playbook/version/hash, brief/version/hash, knowledge snapshot/version/hash і точні input artifact id/version/hash. Джерело має status=approved, scope workspace і застосовні territory/channel/valid_from/valid_to. Конфлікт джерел не вирішується за принципом «новіше краще»: потрібне owner resolution. Термін актуальності задається у knowledge; якщо для мінливих даних немає правила, input_gate блокує та просить визначити його.

Факти про бренд, тариф, швидкість, покриття, адресу CTA, результати кампаній, конкурентів і техліміти каналів походять тільки з pinned knowledge. Продуктне твердження з брифу саме по собі не є затвердженим фактом. У brief дозволені параметри замовлення: кількість, дедлайн, бажана тривалість, канали. Пропоновані календарі, ідеї, експерименти й організаційні строки є рекомендаціями; їх не видають за минулі результати або погоджені плани.

Для кампаній потрібно knowledge.dataset: джерело, reporting period, timezone, currency, grain, визначення колонок, attribution window, approved_by/version, quality flags. Завантажений CSV або звіт не стає knowledge автоматично. Прогноз CPA, лідів чи охоплення без затвердженої моделі не допускається як факт.

`source_uses` прив'язує фактичний фрагмент виходу через JSON Pointer до record_id/version/pointer. Похідна цифра має derivation і Calculation. Всі посилання мають бути в pinned snapshot. Сервер перевіряє існування й застосовність, reviewer - змістове підтвердження твердження. Формальна наявність посилання не доводить істинність.

`claims_needing_source` - невикористані або блокуючі твердження, не «дозвіл на публікацію». disposition=excluded допускається у ready лише якщо твердження виключене з готового контенту й не впливає на висновки. disposition=placeholder або placeholder у видимому контенті означає blocked. Якщо знання відсутнє, не вигадувати навіть кольори, шрифт чи URL з пам'яті чату. Brand knowledge обов'язкове для публічних матеріалів; для аналітичного звіту потрібна щонайменше затверджена термінологія та визначення метрик.

Конкурентні веб-джерела можна збирати вручну офіційними інструментами сесії в candidate_collection. ResearchCandidate не є knowledge; власник перевіряє та імпортує його окремою людською дією. Після затвердження даних потрібен новий versioned run. Схеми не передбачають платного API, автоматичного браузерного обходу чи неофіційних інтеграцій.

## Пакет власнику та передача

`package.sections` - JSON Pointer верхнього рівня фінального build, плюс синтетичний `review`. Порядок масиву є порядком показу. Код не створює нового змісту: показує зазначені поля дослівно та додає версії, статус і блокери. Невказані поля результату залишаються доступними у повному JSON, але не зникають з canonical artifact.

Approval зберігає actor_id, approved_at, run_id, точний manifest/hash final artifact + review + brief + knowledge. Власник може погодити лише ready_for_approval. Для blocked/escalated він розв'язує питання, відхиляє або відкриває новий run. Підтвердження користувача не може мовчки зробити недостовірну ціну перевіреним фактом: спочатку оновлюється knowledge і повторюється контроль у новому run.

`approved_manifest` - синтетичне code-поле handoff за `$defs/ApprovedManifest`. `content` містить run_id, playbook_key/version, brief_ref, knowledge_snapshot_ref, artifact_refs, review_ref; поля *_ref містять id/version/hash. До content додаються content_manifest_hash, approval_id, approved_by, approved_at. `content_manifest_hash` = SHA-256 RFC 8785 canonical JSON тільки content, без approval-метаданих, щоб не створювати циклу хешування. Artifact hash так само рахується з canonical JSON; hashes версій knowledge/brief беруться зі сховища, яке має застосовувати той самий алгоритм. `handoff.payload` копіює вказані поля фінального артефакту й додає review та approved_manifest. Немає переписування, генерації зображень, друку, надсилання SMS чи витрати рекламного бюджету.

Створення handoff ідемпотентне за approval_id + manifest_hash + destination. Стан `handoff_ready` означає «передано до виконання», а не «надруковано/опубліковано/запущено». Для ads_manager - структурований пакет людині, яка налаштовує рекламу; для print - пакет відповідальному за друк. Подальші стани production_started / production_delivered / production_accepted задає людина або окремий локальний продакшн-процес з доказами. Зміни фактичного контенту в продакшні потребують нового контролю й погодження версії.

Під час handoff змінені/відкликані knowledge чи artifacts роблять approval stale. Просте продовження lease не змінює snapshot. Нові знання не підмішуються в активний run. Після owner approval ще раз перевіряються застосовність джерел і дедлайни дії пропозиції.

## Що змінити в рушії, якщо цього ще немає

1. Версійований registry та сумісність старих запусків; reels_concepts v1 не перезаписувати.
2. Компілятор фіксованого графа з review/revise/owner/handoff та явним лімітом змістового rework=1.
3. Окремий blocked outcome: структурно валідна відповідь не означає готовності до продакшну.
4. JSON Schema + semantic validators; обидва виконуються до відкриття наступного кроку.
5. Knowledge snapshot, pointer-level lineage, freshness/territory/status gates і людське затвердження нових джерел.
6. Executor guard: reviewer відрізняється від автора prepare/build/revise, перевірка фактичних авторів артефактів, а не лише початкового плану.
7. Approval і handoff прив'язуються до manifest/hash; повторна передача ідемпотентна, зміна входів робить approval stale.
8. Форми брифу мають використовувати brief-schemas.json; саме поле type=enum у короткому YAML без списку варіантів не є достатнім валідатором.

Фактичну наявність цих механізмів у коді тут не перевірено. Доступні п'ять MCP-операцій не надають код рушія. Нових MCP-методів для цієї бібліотеки не потрібно: контракт get/claim/submit може залишитися тим самим, якщо передає схему, версії й review task.

## Межі перевірки пакета

`python validate_spec.py` перевіряє парсинг YAML/JSON, 12 ключів, всі обов'язкові поля, посилання на схеми, required/properties, seats/executors, P1=5, DAG авторських кроків, посилання package/handoff, ліміти та незалежність reviewer. Потрібен Python із PyYAML (для відтворення використовувалась версія 6.0.3); запитів у мережу немає. Це перевірка цілісності специфікації, не запуск production-рушія й не повний JSON Schema validator. Claude має скомпілювати Draft 2020-12 своїм серверним валідатором і перевірити реальні валідні/невалідні TaskEnvelope на staging/local без платних API.
