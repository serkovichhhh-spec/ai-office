# Семантичні перевірки понад JSON Schema

Виконувати в code до reviewer і повторно до handoff. Блокуючий failure не може бути перекритий середнім балом чи полем decision. JSON Pointer за RFC 6901, екранування ~0/~1.

## Усі плейбуки

1. Перевірити schema, unknown fields, brief types та календарні дати/timezone, output status, deliverable_count за registry.main_output.
2. Унікальні локальні IDs; всі references існують і мають очікуваний тип. SourceUse.output_pointer існує у виході, KnowledgeRef.pointer - у відповідному record/version; claims placeholder affected_pointer може вказувати на відсутнє поле, щоб пояснити блокування.
3. Для status=ready blocking_questions=[]; немає disposition=placeholder і нерозв'язаних обов'язкових входів. Для status=blocked порожні фінальні масиви й null дозволені, а blocking_questions має >=1 елемент; count не примушувати.
4. Meta-count: звичайні плейбуки рахують основний масив. creative_ideation рахує selected_ids, campaign_analysis/competitor_analysis - findings. Адаптації, кадри та допоміжні hypotheses не збільшують deliverable_count.
5. Knowledge refs належать workspace і pinned snapshot; scope/термін дії/territory/channel застосовні. Необов'язкові knowledge refs можна пропустити лише для явно нефактичних creative hypotheses, не для продуктних тверджень.
6. Пошук плейсхолдерів в public-facing copy/дизайні/сценарії. Текст Claim із disposition=excluded не може лишатися у фактичному матеріалі. Це звіряє reviewer; код не вдає повного семантичного розпізнавання фраз. Списки claims та blocking_questions завжди показати власнику.
7. Непорожній destination допустимий лише коли затверджений відповідний knowledge маршрут; null дозволений для матеріалу без CTA за брифом і правилами каналу. Якщо CTA передбачає перехід або перевірку адреси, destination обов'язковий і підтверджений. Не підміняти короткі маршрути доменом з пам'яті.
8. Brand refs та права на AssetUse існують; змінювати/генерувати маскота чи логотип замість використання оригіналу не можна без затвердженої зміни knowledge. Згенерований текст на картинці не є фінальним типографічним шаром.
9. FormatSpec: для готового ТЗ width/height >0, узгоджені з unit й aspect_ratio; для відео duration_seconds >0. Safe area та export_spec перевірити за supplier/platform knowledge; якщо формат не підтверджено, blocked. Жодних універсальних pixel/DPI/bleed defaults.
10. Числа MeasurementPlan.approved_target дозволені лише з target_knowledge_refs; null означає «ціль не затверджена». Decision rule може бути запропонованою умовою експерименту, її позначення як рекомендації зберігається в матеріалі.
11. input_gate не вимагає необов'язкових assets, коли можлива нова зйомка; у такому разі capture_brief і дозволи обов'язкові. Право на відсутній актив не вигадувати.

## Плейбуки

- smm_content_plan: period_end >= period_start, включний період <=93 дні; всі scheduled_at з timezone в цьому періоді; канал входить у channels; capacity відповідає knowledge. Якщо ресурсів недостатньо, blocked із конкретною пропозицією зменшення обсягу, не самовільна зміна brief.
- social_content_pack: kind=content_kind; stories/carousel мають 2-30 frames з послідовними order; short_video має capture_brief з shots. Для нового фото/відео capture_brief не null. Kind=post має frames=[]; зайві кадри не створювати. Кожен unit має design_brief або capture_brief, або source-approved готовий актив у design_brief.asset_uses; порожнє знімальне ТЗ не допустиме.
- graphic_design_pack: creative IDs унікальні; кожне placement брифу покрите принаймні одним formats. adaptation_rules описують переверстку, не механічне обрізання тексту.
- campaign_art_direction: directions 1-3; recommended_direction_id існує; campaign_channels покриті в channel_adaptations. Всі напрями явно дотримуються одного brand snapshot.
- creative_ideation: candidate_count=6..12, selected_count=deliverable_count<=5. Ваги точно 0.35/0.25/0.25/0.15; weighted_score = brief_score*0.35 + distinctiveness_score*0.25 + feasibility_score*0.25 + evidence_score*0.15. Сортування за score descending, нічиї - за concept.id ascending. Вихідні concept IDs збережені, усі кандидати оцінені, selected_ids збігаються з selected=true. Вибір за топом рейтингу; відхилення від нього вважається major issue, а не тихим винятком. Reviewer не сприймає оцінки автора як доказ.
- paid_media_campaign: один platform=brief.platform, рівно один campaign_id, 1-100 ad_sets. ads рівно deliverable_count; кожне входить рівно в один ad_set, всі ad_ids/experiment/budget refs існують. Для кожного ad_set рівно один BudgetLine; сума share_percent=100 з допуском 0.000001. Amount/currency або обидва null (лише коли knowledge затвердило percentage-only planning), або обидва задані й сума/частки збігаються з approved budget. Meta: keywords/negative_keywords=[] та creative != null; Google: принаймні один keyword, creative може бути null для текстового формату лише за knowledge. Реальні назви налаштувань і доступні аудиторні опції потребують platform knowledge, не пам'яті моделі. Кожен A/B експеримент міняє одну змінну, має metric/decision/minimum_evidence/spend guardrail; не вигадувати статистичну потужність.
- reels_concepts: scripts.duration_seconds=brief.duration_seconds; shots починаються з 0, end>start, без прогалин і перетинів, останній end=duration_seconds. Допуск часу 0.01 сек. capture_brief.shots має ті самі order/таймінги, що сценарій; продакшн не отримує дві різні версії. Оцінка вимовності тексту reviewer + людська читка у production_checklist; не видавати її за кодову гарантію.
- outdoor_print_pack: layouts.medium=brief.medium; кожне поле trim/bleed/margin/profile/DPI/scale/finishing відповідає конкретному supplier_spec. Читабельність перевіряється proof у визначеному контексті, не вигаданим «універсальним» лімітом слів. Код перевіряє наявність proof_checks, reviewer оцінює зміст. QR не є єдиним CTA для дорожніх площин.
- offer_launch: units рівно deliverable_count; кожний launch_channel має >=1 unit, тому count>=число каналів. tasks мають валідні depends_on і утворюють DAG; немає залежностей на майбутні незареєстровані AI-кроки. Строки підготовки не пізніше launch_at, якщо це не явно post-launch action в action; channel і роль не означають фактичне призначення конкретній людині. readiness_checklist не є доказом виконання; run не автоматично запускає дочірні плейбуки.
- campaign_analysis: findings рівно deliverable_count; класи fact/derived мають source_refs, derived має calculation_ids. hypothesis має явний план перевірки в actions або assumptions; unavailable не має вигаданого значення. Період порівняння без відповідних даних веде до unavailable, а не домисленої зміни. Подвійний підрахунок/непорівнювана валюта блокує відповідні похідні висновки.
- competitor_analysis: рівно competitors × dimensions rows, унікальні пари. verified => observed_at!=null, observed_value!=null і refs>=1; unavailable => observed_value=null. Findings рівно deliverable_count; за дефіциту фактів допустимі findings з classification=unavailable або hypothesis, без удаваної визначеності. candidate_collection може мати research_candidates лише з реальним retrieved_at/джерелом; knowledge_only вимагає research_candidates=[]. Жодна candidate не використовується як verified row до owner-import у knowledge.
- owned_media_copy: units.kind=copy_kind. email має subject і preheader; інші kind мають subject/preheader=null, крім прямо передбачених delivery knowledge винятків. website/landing/pr/faq мають sections>=1; sms/ivr мають sections=[] і повний текст у copy.body. Довжина SMS й кількість сегментів перевіряються за знаннями кодування/провайдера; якщо їх немає, blocked, не універсальний символічний ліміт. PR-цитата має окремий knowledge ref, IVR не містить непідтвердженого ETA.

## Розрахунки

Calculation - арифметичний вираз зі значеннями з knowledge refs. Використовувати обмежений parser/AST з числами та операціями +,-,*,/ і дужками; ніяких eval, функцій чи доступу до оточення. Назва формули в formula - пояснення, substituted_expression - конкретний дозволений вираз. Зіставити кожне число з input_refs та затвердженим визначенням метрики; константа 100 для відсотків допустима лише як математичне визначення, не зовнішній факт. Відсутній вхід або ділення на нуль => value=null, null_reason непорожній, не false zero. При value!=null null_reason=null.

Числовий допуск порівняння до округлення - max(1e-6, abs(value)*1e-6). Фінальне округлення/валюта - за knowledge metric definition. Reviewer перевіряє, що формула відповідає метриці; код перевіряє арифметику. Якщо parser не підтримує потрібну формулу, результат blocked з точним запитом, а не неперевірена цифра.

## Review і передачі

Рівно п'ять унікальних ключів scores збігаються з YAML criteria. issue.criterion існує в цьому наборі. Немає саморев'ю фактичного автора; manual reassign не обходить guard. decision узгоджений з порогами та issues. review_2 не породжує третє доопрацювання. Невиконаний критерій без issue - структурно-семантична помилка результату рев'ю.

Package містить останню валідну canonical build version і reviewer version. В handoff не включати чернетки старих версій як актуальні. Approved manifest immutable. Handoff не виконується до owner approval і не позначає production completed. Після зміни брифу/джерел/артефактів старий approval непридатний для нового контенту.
